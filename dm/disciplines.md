1. **角色锚定**：prompt 首段写明「你是 de，不是 DM；没有 subagent 工具，不得派子代理」，需要派单时只写「建议 DM 派 X」
2. **fresh 派单**：显式 `context: "fresh"`（不继承父对话），prompt 完全自包含；worktree 由 DM 预建并写明「已存在、直接 cd」
3. **重派先核旧 run**：确认旧 run 已终止才重派，不得复用在跑的 worktree（one writer per cwd）；在跑状态用任务状态接口非阻塞查询（CodeBuddy 任务列表、pi `{action:"status"}`），不靠等待
4. **汇报即消息**：要求子代理按汇报格式直接回给 DM，不另存文档文件；汇报截断不等于未完成，先核 commit 与产物再定性
5. **主工作树纪律**：共享主工作树只做只读与新增提交，amend/reset/rebase 只在自己的 worktree；子代理 commit 前四步（写入 prompt）：`git log -1` 核 base → HEAD 已推进则 `git diff <base>..HEAD -- 本 ticket 文件`（非空即停、上报）→ 显式路径 `git add`（禁 `-A`）→ 绝不 amend/reset 他人 commit。**commit 边界（团队纪律第 15 条，唯一全文见 [`../pm/group-conventions.md`](../pm/group-conventions.md)「团队纪律」表）**：`git commit -- <path>` 只对已跟踪文件生效，新文件（untracked）必须先 `git add`，否则整条命令报 `pathspec … did not match`、什么都不提交。 **worktree 绝对路径纪律（PM 2026-09-29 批准；同日两例同因）**：**工单凡给路径，一律给 worktree 的绝对路径前缀**，并写明「**worktree 建好后所有编辑与命令一律用该绝对路径；严禁在主仓工作树写任何文件或提交任何东西**」。**配套动作**：① 派单时工单首段就写清 worktree 绝对路径（含 `ncnn-android-yolo11/...` 这类子路径的完整前缀）；② 工单写明**误写处置**＝「立刻把改动搬进 worktree ＋ 只对**自己动过的**文件还原主仓 ＋ 贴出主仓与 worktree 的 `git status` 复核 ＋ 回报」；③ 派单前自检：**工单里出现的每个路径是否都带 worktree 前缀**（没有 ⇒ 补上）。**理由（实例）**：**T83／T84 两位 de 先后把改动写进共享主仓工作树**（T84 的 56 行改动与新文件一度停在主仓）⇒ 风险＝**改动被别工单提交扫入**、或**还原时破坏他人未提交改动**；**根因＝工单给的是仓库相对路径**，de 顺手就在主仓编辑（两例同因，属派单模板问题，非 de 个人问题）。**附带登记（同日）**：越界检查脚本若断言「`git status` 必须为空」⇒ 在**共享主仓**会因**他人未跟踪文件**而**假红**（T83 的 `boundary_check.sh` 在主仓复跑 FAIL、在其自己 worktree PASS）⇒ **写这类检查须用「自锚基准 ＋ 显式允许清单」**（同族见第 14 条口径），**不得要求全局干净**。
6. **编号唯一**：ticket 编号由 DM 派单时指定并唯一化（核对 plan 与在跑 ticket），子代理发现冲突停下请示
7. **引用即取源（团队纪律第 24 / 20 / 21 / 99 条）**：DM 执行面＝派单前对每个被引用的 SPEC／判据条目跑原文 grep，把命中原句贴进工单（说不出原句 ⇒ 该引用不算数，禁凭记忆或被压缩的上下文写）；核验只对写入脚本回显的子串跑 `grep -c`，禁止人手重打模式串；报数带 scope；第三方权重与受限许可产物禁入仓，合规归口 PM。**实例**：DM 派 `007-T84` 时把 SPEC-010 §4 A2（原文＝多帧共识：同文本 2 帧复现才上屏＋3s 去重窗口）凭记忆写成「帧内候选解码合并／提速」，由 de 开工前核原文发现并停下回报（处置正确），DM 裁定按 SPEC 原文并作废工单那段
8. **超时必填（团队纪律第 22 条）**：DM 执行面＝写 ticket/prompt 时即填 `timeoutMs`（设备 / 长链路 ≥ 45 min 并按段切分汇报，纯文档工单可短）；来源＝2026-09-23 `007-T01` 未设超时被杀事件
9. **验收复核必声明被复核版本（团队纪律第 25 条）**：DM 执行面＝对 de 产出 / 他方文档做 diff、契约、数值核对时，结论带被复核对象的 commit SHA / 三要素；「留痕 vs 残留」＝旧字面显式标注「作废 / 被取代」
10. **真值素材隔离与元信息隔离（团队纪律第 19 / 19+ 条）**：DM 执行面＝派单时把两条机检写入验收：`material_isolation{drawn_off, overlay_free, evidence}` 缺项 ⇒ `exit 2`；标注工作单不得含被测输出元信息（`prob`/`rank`/`score`/`conf`/`置信`/`top`/`median`/`bottom`，须 0 命中）
11. **台架结论不得直接当真机事实（团队纪律第 23 条）**：DM 执行面＝参数表凡标「实测」者注明测量载体（真机／台架／混合）；台架-only ∧ 涉设备语义 ⇒ 标实测即判失败；台架与真机冲突先怀疑台架语义差异。来源四例＝T49 自死锁／T56 驻留门／T58 `dumpsys` 文本格式／T60 初始态未初始化
12. **改动影响下游消费方 ⇒ 须核对下游并留对照（PM 2026-09-29 批准）**：**凡改动「影响下游消费方」的行为（朝向／几何／尺寸／键语义），须核对下游并留对照；此类工单的验收项必须含一条「下游消费方的可见结果仍正常」**。**依据**：T56 改方向行为入库后，暴露 T05 绘制守卫的硬编码几何假设 ⇒ **框全被丢（`skipped_geom` 占 objects 100%、`drawn=0`）**，而 **T56 的真机验收清单里没有「框是否还在画」这一项** ⇒ 回归没人接住、直到用户报「App 无框」。**机检切片**：验收清单里必须能指出那条「下游可见结果」项；缺失即视为不完整验收。
13. **解码变换不得用在「本来就能解出」的码上，除非先证两次结果一模一样（PM 2026-09-29 批准为通用纪律；来源＝T82 侧发现）**：凡对图像做变换后再解码（**放大、旋转、反色、二值化**等），**只要它可能作用在「本来就能解出」的码上 ⇒ 必须先证明「变换后解出的文字」与「变换前解出的文字」逐字节一致**；证不出来 ⇒ 只能以「**前面都失败才试**」的形式接入（**结构上保证不覆盖已成功的结果**）。**配套动作三件**：① 派单时写明接入方式二选一（失败才试／先给逐字节一致证据），证据＝两臂文字 sha256 比对且 `text_mismatch=0`；② 配**反例臂**：把该变换改成优先／并行试 ⇒ 必须报错或量出不一致（没牙不算）；③ 验收清单里必须有这条。**理由（实例）**：T82 实测 **2 倍最近邻让 169 张本来能解出的样本里 14 张读出不同文字** ⇒ **放大不是无害变换**；A1 的档 2 因写成「失败才试」而安全，但同一变换若用在「已能解出」的码上就会**直接改结果**。
14. **检查必须与自身条件绑定：既不许「因他人而红」（假红），也不许「因缺失而绿」（假绿）（PM 2026-09-29 升格为同族纪律）**：**条款**：凡门禁/检查脚本，其**红与绿只能由「待检对象本身的性质」决定**；**不得把外部条件当判据** -------- ① **他人未跟踪文件**导致越界检查变红（假红）；② **输入素材缺失**（目录在但 0 个文件）导致检查打印「全过」（假绿）。**配套动作**：① 越界/范围类检查一律用**「自锚基准 ＋ 显式允许清单」**（只看本工单基准..HEAD 的差异是否都在清单内），**禁止要求「整仓 `git status` 为空」**；② 素材/输入类检查**必须先判「输入是否存在、数量是否 >0」**，缺失即 **`rc≠0` 并打印缺口**（fail-loud），**不得走「空集 ⇒ 无失败 ⇒ 全过」这条路**；③ **反向臂两向都要有**：**放一个外人未跟踪文件 ⇒ 仍须 PASS**（证明假红修好）＋ **碰一个禁止面的文件 ⇒ 必须 FAIL**（证明牙还在）；**输入侧**：空输入 ⇒ **rc≠0**，有输入 ⇒ 正常判定。**理由（同日两例同族）**：**T83／T84 的 `boundary_check.sh`** 因断言「`git status` 须为空」而在**共享主仓**因**他人未跟踪文件**变红（各自 worktree 里 PASS）；**T80 的 `30-text-check.py`** 在 **roi 目录 0 张素材**时 **`rc=0` 打印全过**（与它自己 README 写的「素材缺失 rc=3」相反，且大产物已清 ⇒ **任何重跑必假绿**）。**共性＝检查结果与自身条件脱钩** ⇒ 两个方向都会让人**信错结论**（假红浪费人工、假绿放过缺陷）。
15. **布局/UI 类工单的核验口径（PM 2026-09-29 定为惯例）**：**布局类改动必须核「打包产物」，不许只看源码**（例：`aapt2 dump xmltree <apk>` 核打包后的 `layout_gravity` / `gravity` / `visibility` / id 等属性）；**配套动作**：① 工单要求贴**打包后属性**的核对输出；② 配**静态检查脚本 ＋ 反向臂**（把属性改坏 ⇒ 必须报红）；**理由**：**源码正确 ≠ 打包正确**（资源合并、变体、aapt 优化都可能改结果），而布局对不对本来就只能在**装出来的东西**上体现（正例＝T89）。
16. **裁定与实现冲突时「意图优先于字面」＋必须主动标出差异（PM 2026-09-29 批准；正例＝T89）**：实现者若发现**照裁定字面做会违反裁定里更硬的目的条款** ⇒ **按目的实现 ＋ 主动标注差异 ＋ 给出代价与改回方案**，由裁定者拍板；**两种做法都禁止**：**静默按字面**（把目的做坏）、**静默改掉**（事后才被发现）。**配套动作**：工单写明「与裁定/SPEC 字面冲突时：按目的实现并在汇报首段标出差异与代价，或停下回报」，**验收时把「有没有主动标注差异」列为检查项**。**理由**：裁定的**目的**才是约束，字面只是当时的最优表述；把两者绑定能同时防「机械执行」与「擅自改道」。**门禁自身也要有牙（DM 同日自我实例）**：**跑门禁时不得用管道吞掉返回码**（`check.sh | tail -1 && git commit` 里的 rc 是 `tail` 的 **0**）⇒ **一律 `set -o pipefail` 或显式 `rc=$?` 进条件分支**；实例＝DM 因此把**一个含长破折号的 skill 违规件提交并推了上去**（随即 fix 提交补正）。
17. **设备掉线类故障＝分层定位再定性（PM 2026-09-29 要求固化）**：**配套动作＝固定四步取证，不许跳步乱试**：① **本侧隧道/端口**：`ss -ltnpe | grep <端口>`（是否 LISTEN、归属）＋ `ss -tnpe | grep <端口>`（**有无僵尸连接**）＋ `ps -eo pid,cmd | grep "ssh .*-[RL]"`（**有无残留隧道进程**）；② **交叉验证**：**另起一个本地 adb server（独立端口、不动环境变量）**看本机 USB 上有没有设备；③ **设备侧**：走隧道问一次 `adb devices`（**能应答但列表为空 ⇒ 隧道通、那头没有设备**），必要时 `lsusb` 看有没有手机；④ **定性**：**能在本侧修的**（僵尸连接/端口占用/隧道残留）**修**；**需人处理的**（USB 掉线、灭屏、Windows 侧 adb server 挂了、需重发隧道）**明确说「需要人在那台电脑前做什么」并转 PM**。**禁止**：反复重启 adb、改环境变量、或切别的路径硬试（**那是在错的层上折腾**）。**理由（实例 2026-09-29 T90）**：手机掉线后分层取证得到「25037 仍 LISTEN ＋ 无僵尸连接 ＋ 隧道应答但设备列表空 ＋ 本地独立 server 也 0 台」⇒ **立刻定性为「那侧无设备、需人处理」**，避免了在 Linux 侧反复折腾；**PM 已把同一前置要求写进 C1 设备段**。
18. **设备工单的「证据可复算」＝精简表入库 ＋ 清理前先导出（PM 2026-09-29 采纳为团队经验；实例 T90/T92）**：**条款**：凡设备采集工单，**结论所依赖的逐条记录（逐框/逐窗行）必须在清理设备侧大产物之前导出并入库**；**只留汇总件＝结论不可独立复算**（复核方无法验收）。**配套动作**：① 采集结束**自动**导出精简表（**只留复算必需列**、落「计数＋哈希」，**不落**原始快照/图片）；② 同时提供**复算脚本**（只读精简表、默认出全部口径）与**机检**（例：判决在两处文件必须一致、抽样数必须标注、精简表存在且可复算）；③ **清理前必须先跑通导出**；导不出 ⇒ **WARN「先别清设备侧快照」并中止清理**；④ **反向臂**：删掉精简表 ⇒ **必须报错**并提示「结论无法独立复算」。**理由（实例）**：T90 收尾把 **1660 份逐框快照**删了 ⇒ 复核方**无法独立复算**头条数、判 FAIL；补精简表（5919 行／324 KB）后复核方用**自写逻辑**复算**逐项一致** ⇒ 机制化之后这类返工不再发生。**同族**：与「门禁探针必须入仓」「证据标准不因成本低而降低」同源。
19. **属性锚只用于「指认」、不用于「取集合」；命名不得撞自己的机检（TM 2026-09-29 两例）**：**(a) 锚的边界**：为避免「各产物编号不同 ⇒ 串味」，我们要求跨产物引用实体时用**稳定属性锚**（如「本体长边范围＋帧数」）；**但锚只是摘要** -------- **要精确取出成员集合，仍须按定义重算**（例：连通分量／聚类规则），**不得用锚的范围做过滤**。**配套动作**：引用锚时**同时写明它是摘要**；凡要「取集合」的地方，**一律按定义算法重算**并给复算命令；**反向臂**：用锚过滤 vs 按定义重算，**两者不一致时以重算为准**并记录差异。**实例**：TM 复核 T96 时先用「本体 218–226」过滤 ⇒ 得 **40 帧/18 ok 且漏了 seq 331**；改用**连通分量**重算 ⇒ **41 帧/19 ok**，与来源一致。**(b) 命名与机检的冲突**：**文件名/路径不要含「会被自己的机检命中的关键词」**（否则检查会**自命中**、产生假红）。**配套动作**：命名前**先跑一次自己的机检**；机检设计上**区分「文件名」与「文件内容」**（内容检查不应扫文件名/目录名）；**反例**：TM 的 `manual-label-truth.tsv` 含 `label` ⇒ **自命中**，改名为 `manual-review-truth.tsv`；de 侧 `codeprobe` 路径含 `prob` ⇒ `-i prob` 假阳性（应写**带词边界**的判法或**最短充分子串**）。**理由**：两组都是「**检查/引用与自身条件脱钩**」的同族（第 14 条），只是这次的隐身衣是**命名**与**摘要**。
20. **含 ncnn 并行实验的 ticket 必写加固清单（TM 建议、DM 2026-09-24 采纳）**：凡派单含 **ncnn 并行 / 多进程推理实验**（host 或设备），ticket**必须**写明三条：① **`spawn` 上下文**（**禁 `fork`**；父进程已跑 ncnn 前向或起过线程后建池，子进程会**静默死锁**）；② **每组合 `timeout` 硬包裹**，并有 `terminate / join / kill` 兜底；③ **逐行增量落盘**（防挂死时丢全部结果）。**判活依据** = 进程 CPU 占比（挂死时常 `< 5%`）＋ 输出 mtime 停滞；**不得**只凭「无输出」判长跑。来源 = 007-T09 `RESULTS.md §3.6`（实测登记）＋ TM 的 `te`（`92eae1ae`）`bash` 挂死 45 min 同类成因
