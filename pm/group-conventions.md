# PDT 集团口径：通信 / 文档 / 命名 / 看板

本文件是 PDT 集团的**唯一规范来源**。

## 组织架构

```
pdt-group（一级部门，负责人 pm：用户入口 ＋ 产品经理）
├── pd   产品部门       经理 pm  → SPEC（自己落笔）
├── dev  开发部门       经理 dm  → 开发计划与进度（自己落笔）
│   └── de × n                单 ticket 实施 → .worktrees/{ticket}
└── test 测试部门       经理 tm  → 测试报告（自己落笔）
    └── te × n                用例执行
```

- 三个经理**自己落笔**本部门文档；不设文档秘书，也不设调研与 SPEC 子代理（2026-09-23 起）
- **pm 兼集团负责人与产品经理**（2026-09-23 起取消独立 leader 角色）：承接用户诉求、组建并管理 dm / tm 会话、顶层裁决
- `de` / `te` 由 DM / TM **按实际情况派生 n 个并行子代理**（n = 可并行 ticket 数 / 可并行批次数，可为 1，不要为凑数硬拆）；子代理只向本部门经理汇报、只接受本部门经理安排
- 经理间直通（pm / dm / tm 横向协商）；两方无法一致时由 pm 裁决

## 通信：herdr 直连，这是主通道

**pm / dm / tm 之间一律用 `herdr` 定向直连**（CLI 语法见 herdr 技能本身），经理之间直接谈，不经第三人转达。

- 状态、进度、结论、缺陷退回、裁决请求，都走 herdr 消息
- 消息自包含：一句话摘要 ＋ 产物路径 ＋ 请求动作
- 收件人按 tab label 现查（label 稳定，pane ID 重启会变），不写死 ID
- 不做轮询：上游更新由用户 / pm 触发，或在本轮任务开始时检查一次
- **不写状态通报文档**：进度靠消息同步，不靠写文件互相感知

## 文档白名单（硬性）

**只允许下面这几类文档文件。** 需要记录的内容一律并进已有文档，**不新建文档类型**（不写会话日志、不写总结、不写「汇报」文档、不给代码配 README）。

| 文档 | 路径 | 上限 | 归属 |
|---|---|---|---|
| SPEC | `docs/pd/spec/spec-{seq}.md` | 80 行 | PM |
| 开发计划与进度 | `docs/dev/plan/{seq}.md` | 50 行 | DM |
| 测试报告 | `docs/test/report/{seq}.md` | 40 行 | TM |
| 领域术语 | `CONTEXT.md` | 按需 | PM |
| 看板（兜底，见下） | `docs/status.md` | 一行一需求 | 三方各管自己的列 |

- 已废除（2026-09-23）：`docs/adr/`（架构决策并入开发计划的「设计决策」节）、`docs/pd/research/`（调研结论直接进 SPEC）、`docs/dev/report/`、`docs/test/plan/`、`docs/dev/evidence/`、`docs/test/evidence/`、`docs/handoff/`（交接改为按需）
- **证据内联**：报告里给 `file:line` 或 grep 结果即可，不落盘证据文件；用户明确要求留存原始输出时才另存，目录当次商定
- **没有内容的节直接删掉**，不写「无」「N/A」「待补充」占位

## 写作纪律

0. **不要每轮都写文档**（硬性）：只在有实质产出或口径变化时才动文档（新 SPEC、升版、计划变更、报告定稿）；日常轮次不落盘，进度与结论走 herdr 消息。文档是被读的产物，不是工作日志
1. **表格一行一条**，不用散文解释表里已有的内容；结论一句话，不写铺垫、不写背景介绍、不写方法论
2. **一次成稿**：除事实错误外不返工润色
3. **超上限就是没写完**，必须删到上限以内
4. **时间预算**：同一 feature 的文档写作累计不超过实现时间的 10%。发现自己在反复改文档，就停下来去做事

## 文件命名

**一份需求一份文档，就地更新**；历史版本由 git 承载，不靠文件名时间戳。

- **`{seq}` 是整条链的锚**：SPEC、开发计划、测试报告共用同一个 seq，由 PM 立 SPEC 时生成（形如 `001-user-sync`），其余沿用
- 升版改同一文件（版本号 `v1.0` / `v1.1` 记在文件头），不新建文件
- 目录缺失时 `mkdir -p`

## 看板（仅 herdr 不可用时的兜底）

默认**不建、不维护** `docs/status.md`。只有当 herdr 完全不可用、必须靠文件互相感知时，才建这张表（只留表头）：

```markdown
# 需求状态看板

| SPEC | 标题 | 开发状态 | 测试状态 | 更新时间 |
|---|---|---|---|---|
| 001-user-sync | 用户同步 | 实施中 | 待编写 | 2026-08-10 |
```

- 一行一个需求，更新时间写绝对日期
- PM：新增行，维护 `SPEC`（seq）与 `标题`；DM：维护 `开发状态`（`规划中` / `实施中` / `已提交` / `待验证`）；TM：维护 `测试状态`（`待编写` / `待执行` / `通过` / `阻塞` / `需修复`）
- pm：只读总览；跨部门裁决结论写进本表
- 由 seq 可推出 `docs/pd/spec/spec-{seq}.md`、`docs/dev/plan/{seq}.md`、`docs/test/report/{seq}.md`
- 看板与实际不一致时，以实际为准并回写看板

## 交接

**默认不写交接文档**：跨角色传递走 herdr 消息。只有用户明确要求时，才用 mattpocock 的 [`/handoff`](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/handoff/SKILL.md) 写一份 ≤ 25 行的自我交接，先 commit 并 push，只写接手所需的最小充分信息。子代理不写交接。

## 会话与 label

会话名固定 `pm` / `dm` / `tm`，label 集合 `{pm, dm, tm}`（pm 是集团入口，dm / tm 由 pm 起）。

## 跨技能引用纪律

- **指针化**：通信规则、文档白名单、命名规则、herdr CLI 语法只留一处（本文件），其余指向它
- **自包含**：验证方法、断言语义这类会被反复改写的具体条目，各技能自己写全，注明「与 X 侧同名同义」，不指向对方，避免对方改表时静默漂移
