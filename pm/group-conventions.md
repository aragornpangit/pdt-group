# PDT 集团口径：通信 / 文档 / 命名 / 看板

本文件是 PDT 集团的**唯一规范来源**。

## 组织架构

```
pdt-group（一级部门，负责人 pm：用户入口 ＋ 产品经理）
├── pd   产品部门       经理 pm  → SPEC（自己落笔）
│   └── pm 子代理 × n         按需派生（取证 / 核查 / 资料整理），只向 pm 汇报，pm 汇总结果
├── dev  开发部门       经理 dm  → 开发计划与进度（自己落笔）
│   └── de × n                单 ticket 实施 → .worktrees/{ticket}
├── test 测试部门       经理 tm  → 测试报告（自己落笔）
│   └── te × n                用例执行
└── scout 集团直属专家  scout    → 调研报告（docs/pd/research/，自己落笔）
    └── 调研子代理 × 1         按需派生，一个研究需求派一个
```

- 各经理**自己落笔**本部门文档；pm 可按需派生子代理干活（取证 / 核查 / 资料整理类），交付文档仍由 pm 汇总后自己落笔
- **pm 兼集团负责人与产品经理**：承接用户诉求、组建并管理 dm / tm 会话、顶层裁决
- `de` / `te`、pm 的子代理、scout 的调研子代理，一律由**派生他的那个经理**按实际情况派生 n 个并行子代理（n = 可并行 ticket 数 / 可并行批次数 / 调研需求数，可为 1，不要为凑数硬拆）；**子代理只向派生自己的经理汇报、只接受该经理安排**，pm 负责汇总自己派生的子代理的工作结果
- **子代理后台派发**（2026-09-24 起）：经理派子代理一律后台/异步，**派完立即结束本轮（return control）**、保持会话可收 herdr 消息，禁止原地等待、轮询、阻塞式等待子代理返回；子代理完成经完成通知（task-notification / 原生唤醒）触发验收或复核。经理可同时持有多个批次。具体开关按你所用的 agent 工具映射（如后台运行参数、async subagent、原生并行 subagents）
- 经理间直通（pm / dm / tm 横向协商）；两方无法一致时由 pm 裁决
- **调研派 scout**：pm / dm 遇到技术选型、竞品对标、重构前评估，派活给 scout 会话（herdr 发给 `scout` label），**不自己拉调研子代理**；scout 的结论一句话回流 SPEC 或开发计划。scout 会话不存在时 pm 先按 [`team-bootstrap.md`](team-bootstrap.md) 起一个

## 通信：herdr 直连，这是主通道

**pm / dm / tm 之间，以及 pm / dm → scout，一律用 `herdr` 定向直连**（CLI 语法见 herdr 技能本身），直接谈，不经第三人转达。scout 只接用户或 pm / dm 的派单，不主动插话。

- 状态、进度、结论、缺陷退回、裁决请求，都走 herdr 消息
- 消息自包含：一句话摘要 ＋ 产物路径 ＋ 请求动作
- **发消息前必须先定位伙伴（硬性，2026-10-04 用户要求）**：先跑 `herdr tab list` 列出当前所有 tab 的 label，确认收件人 label 在列表里，再用该 label 作 `herdr agent prompt <label> "<消息>"` 的目标。**不许凭记忆写 label，不许写死 pane ID 或 tab ID**（label 稳定，ID 重启就变）
- **label 不在列表里 ⇒ 不许发**：先按「会话与 label」补齐会话（补齐流程见 [`team-bootstrap.md`](team-bootstrap.md)），确认就绪再发；不要对一个不存在的会话反复重试
- 不做轮询：上游更新由用户 / pm 触发，或在本轮任务开始时检查一次
- **不写状态通报文档**：进度靠消息同步，不靠写文件互相感知

- **脚本 / 探针不属白名单管辖**：探针 / 单测 / 静态断言脚本是**可复算必需的工具**（第 7 条）⇒ **入仓代码树** `tools/<ticket>/`（不进构建产物）；「证据内联」**只管产物**（截图 / 侧车 / 日志），**不管工具**：「脚本不入仓 ⇒ 按需重建」= 不可复算（重建依赖原脚本 ⇒ 循环）
- **没有内容的节直接删掉**，不写「无」「N/A」「待补充」占位

## 写作纪律

0. **不要每轮都写文档**（硬性）：只在有实质产出或口径变化时才动文档（新 SPEC、升版、计划变更、报告定稿）；日常轮次不落盘，进度与结论走 herdr 消息。文档是被读的产物，不是工作日志
1. **表格一行一条**，不用散文解释表里已有的内容；结论一句话，不写铺垫、不写背景介绍、不写方法论
2. **一次成稿**：除事实错误外不返工润色
3. **行数上限是基准不是目标**（交付物行数可适当放开，2026-09-30 用户指定）：超了先删冗余；删无可删仍需超出时，在文件头登记一行原因，不硬砍信息
4. **时间预算**：同一 feature 的文档写作累计不超过实现时间的 10%。发现自己在反复改文档，就停下来去做事

## 表达（全角色，2026-09-28 用户要求）

**管三个地方：讲话（消息）、写文件（报告 / 计划 / 说明）、写代码注释。** 目标读者 = 稍微懂一点软件工程、但没参与本项目的人（含用户）。各角色 SKILL.md 不再复述本节，只留指针。

- **先说结论，再说依据**：第一句给结论（通过 / 不通过 / 需拍板），依据放后面
- **不造词**：不用自造简称和内部行话；必须用专业词时，**第一次出现加一句白话解释**
- **一段一个意思**，句子短；能给具体例子就不写抽象结论
- **三件事讲清楚**：这是什么、为什么要紧、做了会怎样；写成能照做的动作（谁做、做什么、在哪做、怎样算做对了）
- **数字带上出处**：这个数从哪来、量的是什么、什么时候量的
- **注释同样说人话**：写给「下一个读这段代码的人」，写清「这段在做什么、为什么这么做」，不写只有本团队懂的指代
- **派活的单据**：英文叫 ticket，中文口头叫「派活工单」，不简写成「票」（2026-09-30 全仓）

**配套动作（发出前必须先做）**：自问「**一个懂编程、但没参与这个项目的人，读得懂吗？**」读不懂就改，改完再发。面向用户的汇报另跑黑话 grep 自检：**唯一详细版（黑话对照表 ＋ 自检命令 ＋ 两个例外）见 [`communication-style.md`](communication-style.md)**，各角色不再各维护一份对照表。

## 团队纪律（跳角色，硬性）

> 技术类纪律的**唯一载体 = 本文件**（原 `docs/test/DISCIPLINES.md` / `docs/group/decisions.md` 已废除，2026-09-24）。各角色 `SKILL.md` 只留一行指针与角色特有的执行面，**不再复述全文**（2026-09-29 起取消「两侧闭环」双写，防两份漂移）。
> **元纪律**：纪律必须**配配套动作**（把「记得遵守」变成「必须先发生的动作」）；只写「不许做什么」视为**不完整、可被驳回**。每条还须有**理由**（改法会被人抄走，理由才是「为什么不能省」）。
> **准入门槛（两问，任一答不上 ⇒ 该纪律不成立）**：① **查来源**：它防住的**真实失效形态**是哪一个（能说出失效机制即可，**不必留下项目名与工单号**，具体实例由各角色 `disciplines.md` 承载；连形态都举不出来 ⇒ 还没被违反过的纪律，按「未实测不得当证据」的对偶，不算数）；② **查理由**：写之时若卡在「理由是什么」写不出来 ⇒ 多半没有真实来源，应重新想它在防什么。
> **对偶**：**一个从未跑过的机制，和一条从未被违反过的纪律一样，都不算数** ⇒ 机制须标「首次实跑证据」；纪律须标「它防住的失效形态」。

| # | 纪律 | 配套动作（必须先发生） | 同族 |
|---|---|---|---|
| 1 | `git add` 与 `git commit` 之间不得插入其它动作；`commit -m … -- <path>` 绕过索引 | **新文件（untracked）必须先 `git add`**（否则 `pathspec … did not match`、`rc=1`、**什么都不提交**）；提交前 `git diff --cached --name-only` 复核 | 第 5 条 |
| 2 | 自查与报数必须**实跑最短充分子串**，不得凭记忆外推 | 修正后**重新实跑同一命令**；**任何报数必须先有实跑输出** | 第 4 / 5 / 9 条 |
| 3 | 判据「真值」不得取自**被测对象自身输出**（防循环论证）；也不得与被测对象**共享盲区** | 真值须可**独立复算**；他人预标注只作**下界估计**、不得作召回率最终判定 | 第 4 条 |
| 4 | **报数三件套**：凡对外报出数字，须同时给「① 取值口径 ＋ ② 登记点 ＋ ③ 原始出处（文件／轮次）」。理由＝「凑绿」最常见形态不是造假，而是**换个更好看的数**（口径可对、动机不可判） | 落笔前先把三件写出来；缺任一件视为**不完整汇报、可被驳回**（驳回只说「缺第②项、请补」，不指控人） | 第 2 / 9 条 |
| 5 | **宣告完成须附核验数字**：凡宣告「已落 X」须附 `grep -c`（或等价）输出（**先 0 → 写 → 再 1**），并给「模式串来源」；**核验对象须＝交付对象**。理由＝commit 验「落盘没有」、grep 验「写到位没有」，两门缺一即静默失败 | 写入脚本**回显关键子串**，核验只对该回显串跑 `grep -c`，禁止人手重打；先 `git add` → 再核 → `git diff --cached` 与 `git diff` 均空 → 才 commit；宣称「全仓/远端状态」须先 `fetch` 再核，或显式限定以本地副本为准 | 第 1 / 2 条 |
| 6 | **派单超时必填**：派子代理（新建 / resume）必显式设 `timeoutMs`，**写工单时即填**，不得依赖默认值。理由＝默认 30 min 一到就静默杀掉正在跑的长任务，前面的工时全废且无人知道 | 把 `timeoutMs` 作为工单固定字段；设备 / 长链路 ≥ 45 min 并按段切分汇报；纯文档工单可短 | 元纪律 |
| 7 | **引用即取源**：数值、版本号、许可证等必须从一手产物取，「先 grep 后落笔」，说不出出处不算数；**工单引用 SPEC／判据条目须逐字核过原文再落笔**，禁止凭记忆或被压缩的上下文写 | 派单前对每个被引用条目跑一次原文 grep，把命中原句贴进工单；性能数字给一手出处，转述二手要标注 | 第 4 条 |
| 8 | **复核结论必声明被复核版本**：对他人产物做 diff / 契约 / 数值核对，结论必须带被复核对象的 `commit` 或三要素；跨时点比对不核版本会把「补正后」误当「补正前」 | 下结论前先取对象 SHA（`git rev-parse`）写进结论；「留痕 vs 残留」区分点 = 旧字面是否显式标注「作废 / 被取代」 | 第 4 条 |
| 9 | **关键词命中必标 scope**：报「命中数 / 0 命中」必须同时给 scope | 报数格式固定为「**命中数 ＋ scope ＋ 命令**」三件套；**缺 scope 的命中数 = 无效证据、可被驳回**；scope 跨 ticket ⇒ **按 ticket 分桶** | 第 2 / 4 条 |

## 失败要失败得干净（通用设计偏好，PM 2026-09-29 升格）

**凡工具／脚本／写入操作，失败要失败得干净：要么全成、要么什么都没变**（不留半成品、不留「写了一半」的中间态）。

- **写法**：写文档/改文件一律「先断言、后写入」，断言失败时文件根本没被改，无需清理、也不会被人误读
- **同族**：工具连不上时不要反复重试；`git commit -- <path>` 对未跟踪文件响亮失败优于静默漏文件
- **判据**：失败后工作区/文件与操作前完全一致（可机检：失败 ⇒ `git status` 与操作前相同）

## 文件命名（2026-09-30 起，四类产物统一格式，PM 2026-09-30 定）

`{前缀}-{语义slug}-{YYYY-MM-DD-HH-MM-SS}-v{N}-{seq}.md`

- **前缀四选一**：`pd-spec`（SPEC）／`dev-tickets`（开发计划与 ticket）／`test-report`（测试报告）／`pd-research`（调研报告）。**交接文档不属这四类**，命名见「交接」节
- **语义 slug**：英文短横线连接，不超过 5 个词（如 `user-sync`）
- **时间戳**：该版本首次落盘时刻，格式 `YYYY-MM-DD-HH-MM-SS`
- **版本号 `v{N}`，从 v1 起**：**版本内小步更新**（追加用例、逐 ticket 状态、进度）就地改同一文件、不改名；**实质修订升版落新文件**（新时间戳、`v{N+1}`、seq 不变），旧文件头部就地标注「已被 vX 取代」（留痕 vs 残留：旧字面显式作废，不靠删除冒充没发生）
- **`{seq}` 是整条链的锚**：累计流水号（001 起），放在版本号之后；SPEC、开发计划、测试报告同一需求共用同一个 seq，由 PM 立 SPEC 时生成，其余沿用；Scout 的调研报告用自累计流水号
- **引用同链产物**：按 `{前缀}-*-{seq}.md` 定位（时间戳与版本号不进引用，glob 补齐）
- 目录缺失时 `mkdir -p`

## 看板（仅 herdr 不可用时的兜底）

默认**不建、不维护** `docs/status.md`。只有当 herdr 完全不可用、必须靠文件互相感知时，才建这张表（只留表头）：

```markdown
# 需求状态看板

| SPEC | 标题 | 开发状态 | 测试状态 | 更新时间 |
|---|---|---|---|---|
| 001-user-sync | 用户同步 | 实施中 | 待编写 | 2026-08-10 |
```

- 一行一个需求，更新时间写绝对日期
- PM：新增行，维护 `SPEC`（seq）与 `标题`；DM：维护 `开发状态`（`规划中` / `实施中` / `已提交` / `待验证`）；TM：维护 `测试状态`（`待编写` / `待执行` / `通过` / `阻塞` / `需修复`）
- pm：只读总览；跨部门裁决结论写进本表
- 由 seq 可推出同链三类产物：`docs/pd/spec/pd-spec-*-{seq}.md`、`docs/dev/plan/dev-tickets-*-{seq}.md`、`docs/test/report/test-report-*-{seq}.md`
- 看板与实际不一致时，以实际为准并回写看板

## 交接

- **语义 slug**：英文短横线连接，不超过 5 个词，概括本次交接的主题（例 `user-sync`）
- **时间戳**：落盘时刻，`YYYY-MM-DD-HH-MM-SS`
- **版本号 `v{N}` 从 v1 起**：同一会话内小步补充就地改同一文件、不改名；交接内容实质换血时另立新版本号文件（新时间戳、`v{N+1}`），旧文件头部**就地标注「已被 vX 取代」**
- **无 `{seq}`**：交接文档不属 SPEC / 开发计划 / 测试报告 / 调研报告那四类产物，不挂需求链 seq
- **内容**：25 行基准，超了先删冗余；只写接手所需的最小充分信息；先 commit 再 push
- **子代理（`de` / `te`）不写交接**，一律由经理汇总
- 目录缺失时 `mkdir -p`

## 会话与 label

会话名固定 `pm` / `dm` / `tm`，label 集合 `{pm, dm, tm, scout}`（pm 是集团入口，dm / tm 由 pm 起；scout 由 pm 按需起，或用户直接在其会话下达调研）。**发消息时 `herdr tab list` 里要查的就是这四个 label**：经理之间查 `pm` / `dm` / `tm`，派调研查 `scout`；查得到才发，查不到先补会话。

- **运行时底座与通信优先级（2026-09-29 用户建议）**：优先用 **herdr 作终端运行时底座**，各角色会话尽量跑在 herdr 会话里（一个角色一个会话，label 见上）；会话之间**优先用 `herdr agent prompt` 定向发消息**通信，不靠文件轮询、不靠跨会话转达。herdr 不可用时才回落（兜底见 [`team-bootstrap.md`](team-bootstrap.md) 的手动模式）。

## 跨技能引用纪律

- **指针化**：通信规则、文档白名单、命名规则、herdr CLI 语法只留一处（本文件），其余指向它
- **自包含**：验证方法、断言语义这类会被反复改写的具体条目，各技能自己写全，注明「与 X 侧同名同义」，不指向对方，避免对方改表时静默漂移
